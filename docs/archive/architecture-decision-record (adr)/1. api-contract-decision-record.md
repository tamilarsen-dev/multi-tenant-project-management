# API Contract Decision Record

## Multi-Tenant Project Management API

**Dokumen:** API Contract Decision Record\
**Status:** Seluruh keputusan API-01 sampai API-07 telah disetujui\
**Versi dokumen:** 1.0\
**Konteks:** Node.js, TypeScript, Express, PostgreSQL, Prisma\
**Tujuan:** Menjadi acuan kontrak antara API server dan client sebelum
implementasi endpoint domain.

------------------------------------------------------------------------

## 1. Tujuan dan ruang lingkup

Dokumen ini mencatat keputusan kontrak API untuk Multi-Tenant Project
Management API. Isinya bukan tutorial HTTP dan bukan spesifikasi seluruh
endpoint. Dokumen ini menetapkan aturan lintas-endpoint yang harus
konsisten: bentuk response, status HTTP, error, pagination, serialisasi
resource, versioning, dan idempotency.

Kontrak API adalah kesepakatan yang dapat diandalkan oleh client. Client
seharusnya tidak perlu mengetahui struktur tabel, model Prisma, atau
detail internal server untuk menggunakan API. Karena itu, kontrak harus
stabil meskipun implementasi internal berubah.

Dokumen ini juga mencatat alternatif yang dipertimbangkan, alasan
pemilihan, trade-off, serta hal yang masih perlu ditentukan ketika
implementasi berlangsung. Keputusan yang belum memiliki angka atau
detail operasional eksplisit tidak boleh dianggap sudah ditetapkan.

### 1.1 Prinsip desain

1.  **HTTP semantics first:** gunakan status dan header HTTP sesuai
    maknanya, jangan menduplikasi informasi tanpa alasan.
2.  **Stable public contract:** struktur response tidak boleh terikat
    langsung pada schema database atau model ORM.
3.  **Predictable errors:** client mendapat error code yang stabil dan
    pesan yang aman.
4.  **Tenant isolation:** response, pagination metadata, dan error tidak
    boleh membocorkan data tenant lain.
5.  **Safe retries:** operasi yang rawan diulang harus memiliki strategi
    idempotency.
6.  **Explicit evolution:** perubahan breaking harus memiliki strategi
    versioning dan migrasi client.
7.  **Consistency over cleverness:** pola yang mudah dipahami dan
    diterapkan konsisten lebih berharga daripada abstraksi yang rumit.

# 3. API-01 --- Success Response Format

**Status: DECIDED**

## 3.1 Keputusan

Gunakan **data envelope** untuk response sukses yang memiliki body.
Jangan menambahkan properti `success: true`.

Response satu resource:

``` json
{
  "data": {
    "id": "org_123",
    "name": "Acme"
  }
}
```

Response collection:

``` json
{
  "data": [],
  "meta": {
    "nextCursor": "opaque_cursor_value",
    "hasMore": true
  }
}
```

Aturan:

-   `data` wajib ada pada response sukses yang memiliki body.
-   `meta` bersifat opsional dan digunakan untuk metadata response,
    misalnya pagination.
-   Tidak ada `success: true`.
-   `204 No Content` tidak memiliki response body.
-   Nama properti JSON menggunakan `camelCase`.

## 3.2 Mengapa memilih data envelope?

Envelope memberikan bentuk luar yang konsisten antara response resource
tunggal dan collection. Metadata dapat ditambahkan tanpa
mencampuradukkan metadata dengan atribut resource.

Bentuk ini juga menyediakan ruang evolusi. Misalnya, metadata pagination
dapat ditambahkan pada collection tanpa mengubah struktur setiap item.

## 3.3 Alternatif dan trade-off

### Alternatif A --- Bare resource

``` json
{
  "id": "org_123",
  "name": "Acme"
}
```

**Kelebihan:** - Lebih ringkas. - Tidak ada lapisan nesting tambahan.

**Kekurangan:** - Bentuk response tunggal dan collection dapat terasa
berbeda. - Ruang untuk metadata response menjadi kurang konsisten. -
Jika metadata ditambahkan, struktur response dapat berubah lebih besar.

### Alternatif B --- Data envelope dengan `success`

``` json
{
  "success": true,
  "data": {
    "id": "org_123",
    "name": "Acme"
  }
}
```

**Kelebihan:** - Status sukses terlihat eksplisit di body.

**Kekurangan:** - Mengulang informasi yang sudah disampaikan HTTP
status. - Berpotensi menciptakan kontradiksi, misalnya HTTP 200 tetapi
`success: false`. - Menambah field tanpa memberi informasi penting bagi
client.

### Keputusan akhir

Memilih **data envelope tanpa `success`**. HTTP status menjadi sumber
utama untuk status request, sedangkan `data` memuat hasil operasi.

# 4. API-02 --- HTTP Status Conventions

**Status: DECIDED**

## 4.1 Keputusan

Gunakan status HTTP sesuai semantik operasi. Jangan mengembalikan `200`
untuk semua kondisi hanya karena response body memuat status internal.

### Success status

  -----------------------------------------------------------------------
  Status                              Penggunaan
  ----------------------------------- -----------------------------------
  `200 OK`                            GET, update, atau archive/restore
                                      jika response resource dikembalikan

  `201 Created`                       Resource berhasil dibuat; sertakan
                                      header `Location`

  `202 Accepted`                      Request diterima untuk proses
                                      asynchronous yang belum selesai

  `204 No Content`                    Operasi berhasil dan tidak
                                      memerlukan response body
  -----------------------------------------------------------------------

Contoh create:

``` http
HTTP/1.1 201 Created
Location: /api/v1/organizations/org_123
Content-Type: application/json
```

``` json
{
  "data": {
    "id": "org_123",
    "name": "Acme"
  }
}
```

### Client error status

  -----------------------------------------------------------------------
  Status                              Penggunaan
  ----------------------------------- -----------------------------------
  `400 Bad Request`                   JSON malformed, query atau request
                                      syntax tidak valid

  `401 Unauthorized`                  Authentication hilang, invalid,
                                      expired, atau revoked; sertakan
                                      `WWW-Authenticate: Bearer`

  `403 Forbidden`                     User terautentikasi dan memiliki
                                      membership aktif, tetapi tidak
                                      memiliki permission

  `404 Not Found`                     Resource tidak ditemukan atau
                                      sengaja disembunyikan karena
                                      cross-tenant/no active membership

  `405 Method Not Allowed`            HTTP method tidak didukung oleh
                                      endpoint

  `409 Conflict`                      Conflict atau stale version

  `413 Content Too Large`             Request body melebihi batas

  `415 Unsupported Media Type`        Content type tidak didukung

  `422 Unprocessable Content`         Request dapat dipahami, tetapi
                                      melanggar validation/domain rule

  `429 Too Many Requests`             Rate limit terlampaui; gunakan
                                      `Retry-After` jika relevan
  -----------------------------------------------------------------------

### Server error status

  -----------------------------------------------------------------------
  Status                              Penggunaan
  ----------------------------------- -----------------------------------
  `500 Internal Server Error`         Unexpected internal error

  `502 Bad Gateway`                   Gateway menerima response upstream
                                      yang tidak valid

  `503 Service Unavailable`           Service sementara tidak tersedia,
                                      misalnya dependency penting tidak
                                      tersedia

  `504 Gateway Timeout`               Gateway tidak menerima response
                                      upstream tepat waktu
  -----------------------------------------------------------------------

## 4.2 Aturan authorization dan tenant visibility

Keputusan khusus untuk domain ini:

-   Cross-tenant resource atau user tanpa active membership: `404`.
-   User dengan active membership tetapi tidak memiliki permission:
    `403`.
-   Stale version: `409`.
-   Invalid Issue domain transition: `422`.

Perbedaan `403` dan `404` disengaja. `403` menyatakan resource berada
dalam scope yang boleh diketahui user, tetapi aksinya dilarang. `404`
digunakan untuk menyembunyikan keberadaan resource yang berada di luar
tenant scope atau ketika user tidak memiliki active membership.

## 4.3 Alternatif dan trade-off

### Menggunakan `400` untuk semua kesalahan client

Lebih sederhana, tetapi client kehilangan kemampuan membedakan
authentication, authorization, conflict, rate limit, dan domain
validation. Pemilihan status yang lebih spesifik membuat client dapat
mengambil tindakan yang tepat.

### Menggunakan `404` untuk semua kegagalan akses

Ini lebih kuat dalam menyembunyikan keberadaan resource, tetapi
mengurangi informasi bagi user yang memang sudah berada dalam tenant dan
hanya tidak memiliki permission. Kebijakan proyek memilih `404` untuk
batas tenant/membership dan `403` untuk permission di dalam tenant
aktif.

### Menggunakan `200` dengan error di body

Tidak dipilih karena mengaburkan semantik HTTP dan menyulitkan client,
monitoring, caching, serta tooling.

## 4.4 Trade-off keputusan

Konvensi yang lebih spesifik membutuhkan disiplin implementasi dan
dokumentasi. Namun, hasilnya lebih mudah diprediksi oleh client, lebih
mudah diuji, dan lebih baik untuk observability.

# 5. API-03 --- Error Response Contract

**Status: DECIDED**

## 5.1 Keputusan

Gunakan custom error envelope dengan struktur:

``` json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Resource not found"
  }
}
```

Untuk validation error, `details` dapat disertakan:

``` json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "The request contains invalid fields.",
    "details": [
      {
        "field": "email",
        "code": "INVALID_FORMAT",
        "message": "Email address is invalid."
      }
    ]
  }
}
```

## 5.2 Field contract

  -----------------------------------------------------------------------
  Field                               Aturan
  ----------------------------------- -----------------------------------
  `error`                             Object utama untuk error response

  `error.code`                        Stable machine-readable code

  `error.message`                     Pesan aman dan dapat dibaca manusia

  `error.details`                     Optional; detail terstruktur,
                                      terutama untuk field validation
  -----------------------------------------------------------------------

Request correlation disampaikan melalui response header:

``` http
X-Request-Id: req_abc123
```

Request ID harus sama dengan ID yang dicatat pada structured log untuk
request tersebut.

## 5.3 Aturan keamanan

-   Jangan mengirim stack trace kepada client.
-   Jangan membocorkan SQL, query internal, struktur database,
    credential, token, atau secret.
-   `message` harus aman untuk ditampilkan.
-   Client sebaiknya mengambil keputusan berdasarkan `error.code`, bukan
    mencocokkan teks `message`.
-   `details` hanya memuat informasi yang aman dan relevan untuk
    memperbaiki request.
-   Jangan menduplikasi request ID di response body; header
    `X-Request-Id` menjadi mekanisme correlation utama.

## 5.4 Mengapa custom envelope?

Custom envelope mudah dipahami dan dapat disesuaikan dengan kebutuhan
validation error dan error code domain. Ia juga menjaga format error
tetap konsisten.

## 5.5 Alternatif: RFC 9457 Problem Details

RFC 9457 mendefinisikan format standar Problem Details, umumnya
menggunakan field seperti `type`, `title`, `status`, `detail`, dan
`instance`.

**Kelebihan:** - Standar lintas-ekosistem. - Semantik error
terdokumentasi. - Berguna ketika API perlu mengikuti standar
interoperabilitas yang luas.

**Kekurangan dalam konteks ini:** - Membutuhkan pemetaan tambahan untuk
error code domain dan field-level validation detail. - Tim perlu
menetapkan konvensi extension fields agar kebutuhan aplikasi tetap
terpenuhi.

### Keputusan akhir

Memilih custom envelope. Trade-off-nya adalah tidak langsung memakai
standar Problem Details, sehingga konsistensi internal dan dokumentasi
menjadi tanggung jawab proyek.

# 6. API-04 --- Pagination Contract

**Status: DECIDED**

## 6.1 Keputusan

Gunakan **cursor-based pagination** dengan aturan:

-   Default `limit`: `20`.
-   Maximum `limit`: `100`.
-   `limit` di luar rentang valid ditolak dengan `400`; jangan diam-diam
    mengubah nilainya.
-   Cursor bersifat opaque bagi client.
-   `totalCount` disediakan sebagai exact count untuk seluruh record
    yang cocok dengan filter dan authorization scope pada saat request
    dieksekusi.
-   `totalCount` bukan jaminan snapshot yang konsisten lintas beberapa
    request halaman.
-   `nextCursor` bernilai `null` jika tidak ada halaman berikutnya.
-   `hasMore` berupa boolean.
-   Ordering harus deterministic dan memiliki unique tie-breaker.
-   Cursor harus divalidasi integritasnya dan konteks query-nya oleh
    server.
-   Cursor invalid menghasilkan `400`.
-   Metadata pagination hanya digunakan pada collection endpoint yang
    memang dipaginasi.

Contoh:

``` json
{
  "data": [],
  "meta": {
    "limit": 20,
    "totalCount": 125,
    "nextCursor": "opaque_cursor_value",
    "hasMore": true
  }
}
```

## 6.2 Mengapa cursor-based pagination?

Cursor pagination menggunakan posisi relatif terhadap record terakhir,
bukan nomor halaman. Ini umumnya lebih stabil dan efisien untuk
collection yang terus bertambah, terutama ketika data berubah di antara
request.

Untuk daftar Issue yang dapat terus dibuat atau diperbarui, cursor
pagination mengurangi masalah pergeseran halaman yang sering terjadi
pada offset pagination.

## 6.3 Alternatif: Offset pagination

Contoh:

``` http
GET /api/v1/projects?limit=20&offset=40
```

**Kelebihan:** - Mudah dipahami. - Mudah melompat ke halaman tertentu. -
Cocok untuk dataset kecil atau data yang relatif stabil.

**Kekurangan:** - Database dapat perlu melewati banyak row untuk offset
besar. - Insert/delete di antara request dapat menyebabkan item terlewat
atau muncul berulang. - Kinerja dapat menurun pada offset yang besar.

## 6.4 Alternatif: Cursor tanpa total count

**Kelebihan:** - Lebih ringan karena tidak perlu menghitung seluruh
record yang cocok. - Lebih mudah diskalakan pada collection besar.

**Kekurangan:** - Client tidak mendapat jumlah total item. - UI yang
membutuhkan jumlah total harus menggunakan pendekatan lain.

### Keputusan akhir

Memilih cursor pagination dengan exact `totalCount` karena kebutuhan
client dan kejelasan metadata. Konsekuensinya, count dapat membutuhkan
query tambahan dan berpotensi menjadi biaya performa.

`totalCount` harus menerapkan filter dan authorization scope yang sama
dengan query data. Menghitung tanpa tenant scope dapat membocorkan
jumlah resource milik tenant lain.

Biaya count harus dipantau. Jika terbukti menjadi bottleneck, kebijakan
ini dapat ditinjau ulang berdasarkan evidence, bukan asumsi.

# 7. API-05 --- Resource Serialization Rules

**Status: DECIDED**

## 7.1 Keputusan

Gunakan **explicit response DTO**. Jangan mengembalikan Prisma model
secara langsung kepada client.

Aturan serialisasi:

1.  Setiap response resource menggunakan DTO/projection yang
    didefinisikan secara eksplisit.
2.  JSON property menggunakan `camelCase`.
3.  Timestamp menggunakan ISO 8601 dalam UTC.
4.  Nullable field dikirim sebagai `null`.
5.  Field yang tidak termasuk dalam projection dihilangkan.
6.  Enum dikirim sebagai string, bukan ordinal integer.
7.  Relationship direpresentasikan sebagai ID secara default.
8.  Nested resource hanya dikembalikan jika secara eksplisit diperlukan
    oleh endpoint/use case.
9.  Field sensitif atau internal tidak pernah diekspos.

Contoh:

``` json
{
  "data": {
    "id": "issue_123",
    "title": "Fix authentication",
    "status": "IN_PROGRESS",
    "assigneeMembershipId": null,
    "createdAt": "2026-11-01T10:00:00.000Z"
  }
}
```

## 7.2 Mengapa explicit DTO?

Database model dan API contract memiliki tujuan berbeda.

Model database mengoptimalkan penyimpanan dan integritas data. DTO
mengoptimalkan komunikasi dengan client. Jika Prisma model langsung
dikembalikan, perubahan internal database dapat tanpa sengaja mengubah
response API atau mengekspos field yang seharusnya privat.

Explicit DTO menciptakan batas yang jelas antara persistence layer dan
presentation/API layer.

## 7.3 Alternatif: Return ORM model langsung

**Kelebihan:** - Lebih sedikit mapping code. - Implementasi awal lebih
cepat.

**Kekurangan:** - API terikat pada schema ORM. - Field internal berisiko
bocor. - Perubahan database dapat menjadi perubahan kontrak API tanpa
disengaja. - Bentuk nested relation dapat menjadi tidak konsisten.

## 7.4 Alternatif relationship representation

### ID reference (dipilih sebagai default)

``` json
{
  "projectId": "project_123"
}
```

**Kelebihan:** - Response lebih kecil. - Kontrak lebih sederhana. -
Mengurangi coupling antar-resource.

**Kekurangan:** - Client mungkin perlu request tambahan untuk detail
relasi.

### Nested resource

``` json
{
  "project": {
    "id": "project_123",
    "name": "Platform"
  }
}
```

**Kelebihan:** - Client mendapat data terkait dalam satu response. -
Mengurangi request tambahan untuk kebutuhan tertentu.

**Kekurangan:** - Payload lebih besar. - Risiko over-fetching. - Kontrak
lebih terikat pada struktur relasi. - Perlu aturan konsisten tentang
kedalaman nesting.

### Keputusan akhir

Relationship berupa ID secara default. Nested projection diperbolehkan
jika use case endpoint memang membutuhkannya dan bentuknya ditentukan
secara eksplisit.

## 7.5 Trade-off

Explicit DTO menambah kode mapping dan potensi drift antara model
persistence dan response. Biaya tersebut diterima untuk memperoleh
kontrol kontrak, keamanan field, dan kebebasan mengubah schema internal.

# 8. API-06 --- API Versioning

**Status: DECIDED**

## 8.1 Keputusan

Gunakan **URI versioning** dengan prefix versi:

``` text
/api/v1/organizations
/api/v1/projects
/api/v1/issues
```

Aturan evolusi:

-   Perubahan backward-compatible tetap berada di versi yang sama.
-   Perubahan breaking memerlukan versi baru, misalnya `/api/v2`.
-   Versi lama tidak boleh dihapus secara mendadak.
-   Sebelum versi dihentikan, harus ada kebijakan deprecation dan
    migration period.
-   Dokumentasi OpenAPI harus sesuai dengan versi API masing-masing.

## 8.2 Apa yang disebut breaking change?

Perubahan breaking adalah perubahan yang dapat membuat client yang
sebelumnya valid gagal atau mengubah perilakunya secara tidak
kompatibel.

Contoh: - Menghapus atau mengganti nama field response. - Mengubah tipe
field. - Mengubah makna field yang sudah ada. - Mengubah format request
yang diwajibkan. - Menghapus endpoint atau mengubah semantik
operasinya. - Mengubah enum dengan cara yang membuat client lama tidak
mampu menangani nilai baru.

Catatan: penambahan field biasanya backward-compatible, tetapi tidak
selalu aman untuk semua client. Client yang melakukan strict schema
validation atau exhaustive enum handling dapat tetap terdampak oleh
penambahan tertentu.

## 8.3 Mengapa URI versioning?

Contoh URL secara eksplisit menunjukkan versi kontrak yang digunakan.
Ini mudah terlihat saat debugging, mudah diuji melalui browser/cURL,
mudah dirutekan, dan mudah dipisahkan dalam dokumentasi OpenAPI.

URI versioning tidak dengan sendirinya memutus client. Client lama tetap
dapat menggunakan `/api/v1` selama server masih menyediakan versi
tersebut. Yang merusak kompatibilitas adalah perubahan kontrak yang
tidak kompatibel atau penghentian versi lama tanpa masa transisi.

## 8.4 Alternatif: Header/media-type versioning

Contoh:

``` http
Accept: application/vnd.example.v1+json
```

**Kelebihan:** - URL resource tetap stabil. - Versi kontrak tidak
menjadi bagian path.

**Kekurangan:** - Kurang terlihat ketika debugging URL. - Client harus
mengatur header dengan benar. - Dokumentasi, testing, routing, dan
caching lebih kompleks. - Perlu perhatian pada `Vary` dan perilaku
intermediary cache.

## 8.5 Alternatif: Tanpa versioning eksplisit

**Kelebihan:** - Paling sederhana untuk API kecil dan client yang
dikendalikan satu tim.

**Kekurangan:** - Perubahan breaking menjadi sulit dikelola. - Sulit
mendukung beberapa generasi client secara bersamaan. - Tekanan untuk
mempertahankan kompatibilitas dapat membuat evolusi API lebih rumit.

### Keputusan akhir

Memilih URI versioning `/api/v1`. Trade-off utamanya adalah server dan
tim harus mengelola lifecycle versi, dokumentasi, deprecation, dan
migrasi client.

# 9. API-07 --- Idempotency Policy

**Status: DECIDED**

## 9.1 Masalah yang diselesaikan

Client dapat mengirim request, server berhasil memprosesnya, tetapi
response tidak pernah sampai ke client karena timeout atau koneksi
terputus.

Client tidak selalu dapat mengetahui apakah operasi: - belum pernah
sampai ke server; - sedang diproses; - sudah berhasil tetapi response
hilang; - gagal sebelum perubahan data terjadi.

Jika client mengulang request create secara membabi buta, server dapat
membuat resource duplikat.

Idempotency menyediakan mekanisme agar retry request yang sama tidak
mengulang efek bisnis.

## 9.2 Definisi

Operasi idempotent adalah operasi yang jika dilakukan beberapa kali
dengan request yang sama menghasilkan efek bisnis akhir yang setara
dengan satu kali operasi.

Idempotency tidak sama dengan mencegah double-click saja. Ia juga
relevan untuk retry otomatis, timeout, koneksi terputus, dan concurrent
request.

HTTP mendefinisikan beberapa method seperti GET, PUT, dan DELETE sebagai
idempotent secara semantik. POST umumnya tidak idempotent secara
default. Untuk operasi POST yang perlu aman terhadap retry, aplikasi
dapat menyediakan mekanisme idempotency sendiri.

## 9.3 Keputusan

Gunakan header `Idempotency-Key` untuk operasi create/command terpilih
yang berisiko menimbulkan duplikasi akibat retry.

Contoh:

``` http
POST /api/v1/projects
Authorization: Bearer <token>
Idempotency-Key: 7f83a1...
Content-Type: application/json
```

Kebijakan yang disetujui:

1.  Tidak semua POST wajib menggunakan `Idempotency-Key`.
2.  Gunakan key pada operasi create/command yang rawan retry dan
    memiliki efek bisnis penting.
3.  Scope key berdasarkan actor dan operasi/endpoint.
4.  Simpan request hash agar key yang sama tidak dapat digunakan dengan
    payload berbeda.
5.  Jika request identik diulang, replay hasil operasi pertama, bukan
    menjalankan operasi lagi.
6.  Request bersamaan dengan key yang sama harus ditangani secara atomik
    agar operasi tidak dieksekusi dua kali.
7.  Key memiliki masa retensi terbatas dan kebijakan kedaluwarsa.
8.  Database constraints tetap wajib untuk menjaga business uniqueness
    dan integritas data.

Operasi kandidat yang telah disebutkan: - Create Organization. - Create
Project. - Create Issue. - Create Invitation.

Penerapan akhir per endpoint dilakukan ketika implementasi endpoint
terkait dirancang.

## 9.4 Perilaku yang diharapkan

  -----------------------------------------------------------------------
  Kondisi                             Perilaku
  ----------------------------------- -----------------------------------
  Key sama dan payload sama, request  Replay hasil operasi pertama
  pertama sudah selesai               

  Key sama dan payload berbeda        Tolak dengan `409 Conflict`

  Key berbeda                         Dianggap sebagai operasi baru

  Request pertama dengan key sama     Jangan menjalankan operasi
  masih diproses                      duplikat; tentukan response
                                      sementara yang konsisten

  Key sudah kedaluwarsa/dihapus       Perlakuan mengikuti kebijakan
  sesuai retention policy             expiry yang ditetapkan saat
                                      implementasi
  -----------------------------------------------------------------------

## 9.5 Alternatif: Tanpa idempotency key

Server hanya mengandalkan validasi dan constraint database.

**Kelebihan:** - Implementasi lebih sederhana. - Tidak membutuhkan
penyimpanan dan lifecycle key.

**Kekurangan:** - Retry setelah response hilang dapat membuat resource
ganda. - Client sulit mengetahui hasil request sebelumnya. - Tidak semua
operasi memiliki natural business key yang dapat digunakan untuk
deduplikasi.

## 9.6 Alternatif: Idempotency key untuk semua POST

**Kelebihan:** - Aturan retry terlihat seragam. - Client tidak perlu
mengingat endpoint mana yang mendukung idempotency jika semua POST
menggunakannya.

**Kekurangan:** - Menambah storage, locking/concurrency handling,
cleanup, dan kompleksitas untuk operasi yang tidak memerlukannya. -
Tidak semua POST memiliki efek bisnis yang perlu dideduplikasi. -
Memperluas permukaan implementasi tanpa manfaat sebanding.

### Keputusan akhir

Menerapkan idempotency key secara selektif pada operasi create/command
yang rawan retry. Ini menyeimbangkan keselamatan retry dengan
kompleksitas implementasi.

## 9.7 Idempotency bukan pengganti database constraints

Dua mekanisme ini menyelesaikan masalah berbeda:

-   **Idempotency key:** mengenali pengulangan request/operasi yang
    sama.
-   **Unique constraint/business constraint:** mencegah state database
    melanggar aturan domain.

Misalnya, dua request berbeda dengan key berbeda masih dapat mencoba
membuat Invitation aktif untuk email dan Organization yang sama.
Idempotency key saja tidak mencegah hal tersebut. Constraint database
dan aturan transaksi tetap diperlukan.

## 9.8 Detail yang belum ditetapkan

Kebijakan tingkat tinggi sudah disetujui, tetapi angka dan detail
implementasi berikut belum diputuskan:

-   Durasi retensi key.
-   Struktur tabel penyimpanan idempotency record.
-   Apakah response replay menyimpan status, header tertentu, dan body
    secara penuh.
-   Response persis untuk request concurrent yang pertama masih
    berjalan.
-   Kebijakan cleanup record kedaluwarsa.
-   Apakah seluruh endpoint kandidat langsung mengaktifkan mekanisme ini
    pada rilis pertama.

Detail ini dapat ditentukan ketika merancang implementasi idempotency.
Jangan menganggap angka retensi tertentu telah disetujui.

# 10. Cross-cutting rules

Aturan berikut berlaku lintas area API Contract:

## 10.1 Tenant isolation

-   Semua query resource harus dibatasi berdasarkan tenant scope dan
    authorization.
-   `totalCount` harus menggunakan scope yang sama dengan query
    collection.
-   Cursor tidak boleh dapat digunakan untuk membaca data di luar
    query/tenant scope asalnya.
-   Error handling tidak boleh membocorkan keberadaan resource tenant
    lain.
-   DTO hanya boleh memuat field yang boleh dilihat oleh actor.

## 10.2 Stable machine-readable contract

-   Client menggunakan HTTP status untuk kategori hasil request.
-   Client menggunakan `error.code` untuk mengenali jenis error
    aplikasi.
-   Client tidak boleh bergantung pada teks `message` sebagai
    identifier.
-   Perubahan pada code, field, enum, dan status harus ditinjau sebagai
    perubahan kontrak.

## 10.3 Documentation

OpenAPI harus mendeskripsikan: - Path dan HTTP method. - Request
parameter, header, dan body. - Success response. - Error response dan
status yang mungkin. - Authentication requirements. - Pagination
metadata. - Idempotency header pada endpoint yang mendukungnya. - Versi
API yang didokumentasikan.

Dokumentasi harus diperbarui bersama perubahan kontrak, bukan setelah
client menemukan ketidaksesuaian.

# 14. Change management

Setiap perubahan terhadap keputusan API Contract harus:

1.  Mengidentifikasi keputusan/section yang berubah.
2.  Menjelaskan alasan dan evidence.
3.  Menguraikan dampak terhadap client dan endpoint yang sudah ada.
4.  Membandingkan alternatif yang relevan.
5.  Menilai apakah perubahan backward-compatible.
6.  Memperbarui OpenAPI dan contract tests.
7.  Mencatat keputusan dan tanggal revisi.

Jika perubahan breaking, perubahan harus mengikuti strategi versioning
pada API-06.

**Prinsip akhir:** API Contract adalah produk yang digunakan client,
bukan sekadar bentuk JSON yang kebetulan dikeluarkan server. Stabilitas,
keamanan, dan evolusinya harus dikelola secara sengaja.
