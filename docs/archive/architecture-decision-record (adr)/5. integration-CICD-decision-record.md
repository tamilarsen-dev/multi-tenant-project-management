## 3. IC-01 — Git Workflow

**Decision:** Use GitHub Flow with short-lived feature branches.

### Rules

1. `main` is the primary integration branch.
2. Every task uses a focused feature or fix branch.
3. Branches are created from the latest `main`.
4. All changes enter `main` through Pull Requests.
5. Direct commits to `main` are prohibited.
6. Use Conventional Commits.
7. Avoid long-lived branches.
8. Do not introduce `develop`, `release`, or `hotfix` branches by default.

### Example branch names

```text
feat/auth-registration
feat/organization-creation
fix/session-refresh-race
refactor/issue-service
```

### Rationale

GitHub Flow keeps branching simple and encourages frequent integration. More complex branching strategies can be introduced if future release requirements justify them.

---

## 4. IC-02 — Pull Request Policy

**Decision:** Pull Requests are mandatory for integration into `main`.

### Rules

1. CI must pass before merge.
2. For team collaboration, require at least one approval.
3. Self-review is acceptable when working alone.
4. Each PR should represent one logical change.
5. PR descriptions must explain:
   - What changed.
   - Why it changed.
   - How it was tested.
   - Migration or configuration impact.
   - Known risks.
6. Use Squash Merge.
7. Delete merged feature branches when no longer needed.

### Rationale

Squash Merge keeps the `main` history concise. Each merged PR becomes one logical commit, simplifying history review and revert operations.

## 5. IC-03 — CI Pipeline

**Decision:** CI runs automatically on Pull Requests targeting `main` and pushes to `main`.

### Required pipeline

```text
Checkout
   ↓
Setup pnpm
   ↓
Setup Node.js
   ↓
Install Dependencies (frozen lockfile)
   ↓
Prisma Generate
   ↓
ESLint
   ↓
TypeScript Typecheck
   ↓
Build
   ↓
Unit Tests
   ↓
Integration Tests
   ↓
Critical E2E Tests
```

### Rules

1. Use `pnpm install --frozen-lockfile`.
2. Commit `pnpm-lock.yaml`.
3. Run Prisma Client generation.
4. Run ESLint.
5. Run TypeScript typecheck.
6. Run production build.
7. Run Unit and Integration tests.
8. Run critical E2E tests when runtime remains reasonable.
9. Use dependency caching as a performance optimization.
10. CI must not silently modify source code or the lockfile.
11. Required pipeline failures must block merge.

### Rationale

Frozen installation and a committed lockfile improve dependency reproducibility. Caching improves speed but is not a source of dependency truth.

## 6. IC-04 — Quality Gates

**Decision:** Required CI checks must pass before merge.

### Required quality gates

| Check | Requirement |
|---|---|
| Dependency installation | Frozen lockfile installation succeeds |
| Lint | No lint errors |
| TypeScript | Typecheck succeeds |
| Build | Production build succeeds |
| Unit tests | All required tests pass |
| Integration tests | All required tests pass |
| E2E | Critical workflows pass |
| Migration | Applies successfully to test database |
| Security | Unresolved critical vulnerabilities block release |

### Branch protection

Protect `main` with:

1. Mandatory Pull Requests.
2. Required status checks.
3. Approval according to the PR policy.
4. Force push disabled.
5. Branch deletion disabled.

### Coverage policy

No global code coverage threshold is mandated for v1.

Coverage may be introduced later when the test suite is sufficiently mature and meaningful thresholds can be established.

### Security policy

Critical vulnerabilities must not be ignored merely to obtain a green pipeline. Vulnerability severity and actual exposure should inform remediation priority.

## 7. IC-05 — Migration in CI/CD

**Decision:** Production migrations run as a separate, controlled deployment step.

### Rules

1. All migrations are created using Prisma Migrate.
2. Migration files are committed to Git.
3. CI tests migration from a clean database using the complete migration history.
4. Migration SQL is reviewed, especially potentially destructive or expensive changes.
5. Production uses `prisma migrate deploy`.
6. Do not use `prisma migrate dev` or `prisma db push` as the production migration workflow.
7. Production migration must not be independently executed by every API instance during startup.
8. Required migration must complete successfully before the new application version receives traffic.
9. Migration failure stops the application deployment.
10. Risky migrations require a backup and recovery strategy.

### Migration sequence

```text
Migration Review
      ↓
CI Migration Test
      ↓
Release Preparation
      ↓
Controlled Production Migration
      ↓
Application Deployment
      ↓
Health Check
```

### Compatibility

Use Expand–Migrate–Contract for risky schema changes.

Application and database compatibility must be considered together. A successful schema migration does not automatically mean the new application version is safe to deploy.

## 8. IC-06 — CD Strategy

**Decision:** Use Continuous Delivery rather than Continuous Deployment.

### Environment strategy

| Environment | Purpose |
|---|---|
| Development | Development and debugging |
| Staging | Pre-production validation |
| Production | Real user traffic |

### Deployment flow

1. CI validates the Pull Request.
2. Changes are merged into `main`.
3. A build artifact is created.
4. The artifact is deployed to staging automatically when staging is available.
5. Smoke tests and validation run in staging.
6. Production deployment requires manual approval.
7. Production migration runs as a controlled step.
8. The new application version is deployed.
9. Health checks and smoke tests verify the deployment.

### Build once, deploy many

Build the application once and promote the same artifact across environments.

Environment-specific configuration and secrets are injected separately.

For Docker deployments, use immutable image identifiers such as image digests.

### Deployment strategy for v1

**Decision:** Use Recreate Deployment with one API instance.

Characteristics:

- Stop the old application.
- Start the new application.
- Verify health.
- Accept brief deployment downtime.

### Deferred strategies

The following are not required for v1:

- Rolling deployment.
- Blue-Green deployment.
- Canary deployment.
- Multi-instance orchestration.

These can be introduced when availability and scaling requirements justify them.

### Secrets and configuration

1. Separate staging and production secrets.
2. Restrict secret access by environment.
3. Do not commit secrets to Git.
4. Do not print secrets in CI logs.
5. Do not embed secrets in Docker images or build artifacts.

## 9. IC-07 — Release & Rollback

**Decision:** Use Semantic Versioning and independently manage application rollback and database recovery.

### Semantic Versioning

Format:

```text
MAJOR.MINOR.PATCH
```

| Version component | Meaning |
|---|---|
| MAJOR | Breaking changes |
| MINOR | Backward-compatible features |
| PATCH | Backward-compatible fixes |

Example:

- `1.0.0`: First stable release.
- `1.1.0`: New backward-compatible feature.
- `1.1.1`: Backward-compatible bug fix.
- `2.0.0`: Breaking change.

Prerelease identifiers may be used, such as `1.0.0-rc.1`.

### Release identification

Each release must be traceable to its source and artifact.

Use:

- Git tags such as `v1.0.0`.
- GitHub Releases for release notes.
- Versioned Docker image tags.
- Immutable Docker image digests.

Do not rely exclusively on the mutable `latest` tag as deployment identity.

### Rollback rules

1. Retain the previous release artifact.
2. Stop a failed deployment before it receives traffic where possible.
3. If the new application version fails after deployment, restore the previous application artifact.
4. Verify health after rollback.
5. Record deployment failures and rollback events.
6. Do not assume database migrations are automatically reversed when application rollback occurs.
7. Use forward-fix migrations when reversing a migration is unsafe.
8. Destructive changes require explicit recovery planning.

### Application rollback vs database rollback

These are separate operations.

Restoring an older application binary does not restore an earlier database schema or recover deleted data.

Expand–Migrate–Contract helps maintain compatibility between application versions and database schema during transitions.

### Release notes

Each release should document:

- Added.
- Changed.
- Fixed.
- Security.
- Migration.
- Breaking Changes.

## 10. Cross-Cutting Principles

The approved decisions establish these principles:

1. `main` is protected and remains the primary integration branch.
2. Every change passes through Pull Request and CI.
3. CI verifies code quality and application behavior.
4. Database migration is versioned, reviewed, and controlled.
5. The same build artifact is promoted across environments.
6. Production deployment requires explicit approval.
7. Release artifacts must be identifiable and reproducible.
8. Application rollback and database recovery are separate concerns.
9. Secrets remain outside source code and build artifacts.
10. Deployment and release history must be traceable.

## 11. Implementation Verification Requirements

During implementation and operational setup, verify:

- Branch protection prevents direct integration without required checks.
- Pull Request workflows run correctly.
- CI uses frozen dependency installation.
- Migration can be applied from a clean database.
- Production migration runs only through the controlled deployment process.
- Staging and production use separate configurations and secrets.
- The same artifact can be promoted between environments.
- Production approval is required.
- Deployment health checks detect failed application startup.
- Previous artifacts can be redeployed.
- Database recovery procedures are documented.
- Release tags and release notes are traceable.

These are future implementation and verification requirements, not claims that every deployment capability is already configured.
