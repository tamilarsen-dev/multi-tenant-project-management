## 3. DI-01 — Transaction Boundaries

**Decision:** Transaction boundaries follow business use cases, not individual database queries.

### Rules

1. All database changes forming one business invariant must be atomic.
2. Required Activity creation must happen in the same transaction as the corresponding business mutation.
3. Issue number allocation and Issue creation must happen in the same transaction.
4. Membership revocation and Issue unassignment must happen in the same transaction.
5. Invitation acceptance and Membership activation must happen in the same transaction.
6. Outbox events must be persisted in the same transaction as their associated business mutation.
7. Email delivery and other external network operations happen after database commit.
8. Transactions should be short and must not wait for external network calls.

### Rationale

A transaction provides all-or-nothing behavior. If one required database operation fails, the entire transaction rolls back.

External systems such as email providers cannot participate directly in a PostgreSQL transaction. The transactional outbox pattern addresses this boundary.

## 4. DI-02 — Database Constraints

**Decision:** PostgreSQL must enforce data invariants that can be represented through database constraints.

### Required mechanisms

| Mechanism | Purpose | Project example |
|---|---|---|
| PRIMARY KEY | Unique row identity | `users.id` |
| FOREIGN KEY | Referential integrity | Issue references an existing Project |
| UNIQUE | Prevent duplicate values or combinations | One Membership per User and Organization |
| NOT NULL | Require a value | Issue title |
| CHECK | Restrict valid values | Positive Issue number |
| Composite FK | Enforce multi-column relationship integrity | Issue and Project belong to the same Organization |
| Partial unique index | Enforce conditional uniqueness | One pending Invitation per Organization and email |

### Specific rules

- Membership: `UNIQUE (organization_id, user_id)`.
- Issue numbering: `UNIQUE (project_id, number)`.
- Issue–Project tenant consistency: composite foreign key involving `organization_id` and `project_id`.
- Invitation: partial unique index on `(organization_id, normalized_email)` where status is `PENDING`.

### Application responsibilities

Application validation remains necessary for understandable error messages and business rules.

Database constraints remain the final integrity boundary when concurrent requests or application defects occur.

Rules involving multiple rows or broader business conditions must be handled through transactions and concurrency control when ordinary constraints cannot represent them.

## 5. DI-03 — Concurrent Number Allocation

**Decision:** Allocate Issue numbers using atomic PostgreSQL `UPDATE ... RETURNING`.

Each Project maintains a `next_issue_number` counter.

Example:

```sql
UPDATE projects
SET next_issue_number = next_issue_number + 1
WHERE id = $1
RETURNING next_issue_number - 1 AS allocated_number;
```

### Rules

1. Each Project has its own counter.
2. Allocation uses atomic `UPDATE ... RETURNING`.
3. Counter allocation, Issue creation, and Activity creation happen in one transaction.
4. `UNIQUE (project_id, number)` remains as a final integrity safeguard.
5. If the transaction rolls back, the counter increment rolls back as well.
6. The design does not promise gapless numbering under every possible administrative or future data operation.

### Rationale

The atomic update serializes competing modifications to the same Project counter through PostgreSQL row-level locking.

A normal `SELECT` followed by an independent `UPDATE` is insufficient because concurrent transactions can read the same counter value.

## 6. DI-04 — Membership Concurrency

**Decision:** Use row-level locking to serialize Membership changes and operations that depend on active Membership status.

### Rules

1. Membership revocation and re-invitation run inside transactions.
2. Use `SELECT ... FOR UPDATE` when the Membership state must be serialized.
3. Operations that modify Issues must verify active Membership under the agreed locking protocol.
4. Revocation and unassignment of all affected Issues must be atomic.
5. Re-invitation reactivates the existing Membership record.
6. Re-invitation updates the role and relevant timestamps according to the existing domain rules.
7. Use consistent lock acquisition order to reduce deadlock risk.

### Concurrent operation behavior

- If an Issue update acquires the Membership lock first, it may complete before revocation.
- If revocation acquires the lock first, the waiting Issue update must re-check Membership state and fail after revocation commits.

The order in which operations acquire the required lock determines their serialization order.

## 7. DI-05 — Invitation Concurrency

**Decision:** Lock an Invitation before checking its status and expiration.

### Rules

1. Use row-level locking when accepting or revoking an Invitation.
2. Check `status` and `expires_at` after obtaining the lock.
3. Invitation acceptance, Membership activation, Activity creation, and relevant Notification creation must happen in one transaction.
4. Use conditional updates as an additional safeguard, such as updating only when the current status is `PENDING`.
5. Keep the partial unique index for active Invitations.
6. Concurrent attempts to accept the same Invitation must not both succeed.
7. If acceptance and revocation happen concurrently, the operation acquiring the lock first determines the outcome.
8. Email delivery remains outside the transaction and uses the transactional outbox.

### Expiration rule

`expires_at` is authoritative.

An Invitation cannot be accepted if `expires_at <= now()`, even if its status has not yet been updated from `PENDING` to `EXPIRED`.

## 8. DI-06 — Activity Atomicity

**Decision:** Required Activity records must be atomic with their associated business mutations.

### Rules

1. Business mutations and required Activity creation happen in the same transaction.
2. If Activity creation fails, the associated business mutation rolls back.
3. Activity is append-only through the API.
4. Activity records meaningful business changes, not reads or every request.
5. `actor_id` may be `NULL` for automated system operations.
6. Activity metadata uses a versioned JSONB envelope.
7. The envelope contains:
   - `schemaVersion`
   - `entityType`
   - `entityId`
   - `changes`
8. Metadata must not contain passwords, session tokens, Comment bodies, or other sensitive secrets.
9. Activity is a historical record, not a replacement for primary business data or an event broker.

### Activity and Notification distinction

- **Activity:** records what changed in the system.
- **Notification:** tells a relevant user about a change.

Relevant Notifications that are part of a business operation must be created in the same transaction.

External delivery remains asynchronous and happens after commit.

## 9. DI-07 — Optimistic Concurrency

**Decision:** Use version-based Optimistic Concurrency Control (OCC) on relevant resources.

### Rules

1. Relevant resources contain an integer `version` column.
2. Clients submit the version they last read when updating a resource.
3. Updates use a conditional operation based on resource identity and expected version.
4. Successful updates increment the version atomically.
5. If no row matches the expected version, return HTTP `409 Conflict`.
6. Versioning is not automatically required for every table.

Example:

```sql
UPDATE projects
SET name = $1,
    version = version + 1
WHERE id = $2
  AND version = $3
RETURNING *;
```

If no row is returned, the expected version is stale and the update must not silently overwrite newer data.

### OCC and pessimistic locking

These mechanisms serve different purposes:

- **Pessimistic locking:** prevents competing operations from proceeding simultaneously on locked rows.
- **Optimistic concurrency:** detects that data changed since the client last read it.

Use OCC for relevant user-facing updates and row-level locking for operations requiring strict serialization, such as Membership and Invitation state transitions.

## 10. DI-08 — Migration Discipline

**Decision:** Use versioned Prisma Migrate with reviewed SQL migrations.

### Rules

1. Migration files are versioned and committed to Git.
2. Use Prisma Migrate to manage schema evolution.
3. Generated SQL must be reviewed, especially changes involving foreign keys, indexes, constraints, and potentially expensive locks.
4. Production schema changes use `prisma migrate deploy`.
5. Do not use `prisma migrate dev` or `prisma db push` as the production migration workflow.
6. Avoid destructive migrations without a data-handling strategy.
7. Use Expand–Migrate–Contract for risky or compatibility-sensitive changes.
8. Take backups before risky production migrations.
9. Do not assume every migration can be safely reversed with a simple rollback.

### Expand–Migrate–Contract

**Expand**
- Add new columns, tables, or structures.
- Preserve compatibility with the currently running application where possible.

**Migrate**
- Backfill or transform existing data.
- Move application reads and writes to the new structure.
- Verify data consistency.

**Contract**
- Remove obsolete structures only after they are no longer used.

### Rationale

Schema changes affect both stored data and application compatibility. A migration must account for existing records and potentially running application versions.

## 11. Cross-Cutting Principles

The eight decisions establish the following principles:

1. Database constraints protect structural data integrity.
2. Transactions protect multi-operation business invariants.
3. Row-level locking serializes operations that must not race.
4. OCC detects stale client updates.
5. Activity and required Notification records remain consistent with business mutations.
6. External side effects are performed after commit through asynchronous mechanisms.
7. Database schema changes are versioned, reviewed, and executed through controlled migrations.
8. Application-level authorization and validation remain necessary; database integrity mechanisms do not replace them.

## 12. Implementation Verification Requirements

The following behaviors must be verified during implementation and testing:

- Failed Issue creation rolls back counter allocation.
- Concurrent Issue creation does not generate duplicate numbers.
- Duplicate Membership creation is rejected by database constraints.
- An Issue cannot reference a Project from another Organization.
- Concurrent Membership revocation and Issue updates produce a consistent outcome.
- Re-invitation and revocation cannot leave Membership in an inconsistent state.
- Concurrent Invitation acceptance cannot activate the same Invitation twice.
- Expired Invitations cannot be accepted.
- Activity failure rolls back the associated business mutation.
- Required Notification creation remains consistent with its business operation.
- Stale OCC updates return `409 Conflict`.
- Migration history is reproducible from a clean database.
- Risky migrations have a documented data and recovery strategy.

These are implementation and verification requirements, not claims that the behavior has already been implemented.
