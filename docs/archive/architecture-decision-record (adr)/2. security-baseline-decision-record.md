# Security Baseline Decision Record

## Multi-Tenant Project Management API

**Versi:** 1.0\
**Status:** SEC-01 sampai SEC-08 disetujui pada level kebijakan\
**Stack:** Node.js, TypeScript, Express, PostgreSQL, Prisma, Zod, Pino

## 1. Tujuan dan ruang lingkup

Dokumen ini merekam kebijakan keamanan minimum proyek sebelum API
menangani autentikasi dan data organisasi. Dokumen ini bukan bukti bahwa
kontrol telah diimplementasikan atau diaudit. **DECIDED** berarti
kebijakan disetujui; implementasi dan pengujian tetap harus dilakukan.

Prinsip: 1. Defense in depth: jangan bergantung pada satu lapisan. 2.
Deny by default dan least privilege. 3. Enforcement dilakukan
server-side. 4. Kegagalan tidak boleh membocorkan data atau credential.
5. Batasi ukuran input dan biaya operasi. 6. Threshold operasional
ditentukan berdasarkan evidence. 7. Scope yang ditunda harus memiliki
batasan yang jelas.

## 3. SEC-01 --- Password Security

**Status: DECIDED**

### Keputusan

-   Password hashing menggunakan **Argon2id**.
-   Salt unik per password, dikelola library hashing.
-   Parameter Argon2id ditentukan melalui benchmark pada environment
    deployment.
-   Minimum password 12 karakter.
-   Maximum length ditetapkan eksplisit saat implementasi.
-   Tidak mewajibkan kombinasi kapital, angka, atau simbol.
-   Whitespace diperbolehkan.
-   Jangan melakukan trimming atau normalisasi diam-diam.
-   Password tidak pernah disimpan plaintext atau ditulis ke log.
-   Perlindungan terhadap password umum/bocor direkomendasikan jika
    mekanismenya tersedia.

### Alasan

Password biasanya memiliki entropy relatif rendah dan dapat ditebak.
Argon2id dirancang untuk membuat setiap percobaan tebakan lebih mahal
melalui memory cost, time cost, dan parallelism.

Parameter terlalu rendah melemahkan perlindungan. Parameter terlalu
tinggi dapat menghabiskan resource server saat login serentak. Karena
itu perlu benchmark.

### Alternatif

-   **bcrypt:** matang dan luas digunakan, tetapi memiliki batas input
    72 byte yang perlu ditangani dengan benar.
-   **scrypt:** memory-hard dan valid, tetapi tidak memberi alasan kuat
    untuk dipilih dibanding Argon2id pada proyek baru ini.

### Trade-off

Argon2id cocok untuk password hashing modern, tetapi membutuhkan tuning
CPU/memori. Tidak ada parameter numerik yang disepakati sebelum
benchmark.

## 4. SEC-02 --- Authentication Protection

**Status: DECIDED**

### Ancaman

  -----------------------------------------------------------------------
  Ancaman                 Cara kerja              Dampak
  ----------------------- ----------------------- -----------------------
  Brute-force             Banyak tebakan password Account compromise
                          untuk satu akun         

  Credential stuffing     Menggunakan kredensial  Account takeover
                          bocor dari layanan lain 

  Account enumeration     Membedakan akun         Daftar akun valid
                          terdaftar dan tidak     terekspos

  Automated abuse         Bot mengirim request    Resource exhaustion
                          autentikasi masif       
  -----------------------------------------------------------------------

### Login failure response

Email tidak ditemukan dan password salah menghasilkan respons generik
yang sama:

``` http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer
```

``` json
{
  "error": {
    "code": "INVALID_CREDENTIALS",
    "message": "Email or password is incorrect."
  }
}
```

Aturan: - Jangan mengungkap apakah email terdaftar atau status akun. -
Untuk email yang tidak ditemukan, lakukan dummy password hash
verification menggunakan hash valid yang disiapkan. - Upayakan perbedaan
waktu pemrosesan kedua kondisi tidak terlalu mencolok.

### Throttling

Gunakan **progressive throttling**, bukan hard account lockout. Hard
lockout memungkinkan penyerang mengunci akun korban dengan sengaja.
Progressive throttling meningkatkan pembatasan seiring percobaan gagal
tanpa langsung mengunci akun permanen.

Threshold dan durasi belum ditetapkan; ditentukan melalui konfigurasi
dan tuning.

### Registration dan recovery

-   Password recovery, jika tersedia, menggunakan respons generik.
-   Registration enumeration ditangani tersendiri saat endpoint
    dirancang.
-   Kebijakan registration final dapat mempertimbangkan verifikasi
    email.

Contoh pesan recovery:

``` json
{
  "data": {
    "message": "If an account exists, instructions will be sent."
  }
}
```

### Security event logging

Catat timestamp, account identifier tersamarkan/di-hash, source IP
relevan, hasil autentikasi, dan request ID. Jangan mencatat password,
session token, atau credential mentah.

### Trade-off

Respons generik mengurangi informasi bagi penyerang, tetapi membuat
feedback pengguna dan debugging kurang langsung. Security event membantu
investigasi tanpa membocorkan credential.

## 5. SEC-03 --- Rate Limiting

**Status: DECIDED**

### Tujuan

Membatasi request untuk menjaga availability, menghambat automated
abuse/brute-force, dan mencegah satu client mendominasi kapasitas.

### Scope

  -----------------------------------------------------------------------
  Scope                   Keputusan               Tujuan
  ----------------------- ----------------------- -----------------------
  Global                  Diterapkan              Melindungi resource API

  Per IP                  Diterapkan              Membatasi automated
                                                  abuse

  Per account             Diterapkan untuk        Menghambat brute-force
                          autentikasi             

  Per endpoint            Diterapkan pada         Melindungi operasi
                          endpoint sensitif       berisiko
  -----------------------------------------------------------------------

### Algoritma

Gunakan **token bucket** sebagai algoritma umum. Token bucket
mengizinkan burst terbatas sementara refill rate mengendalikan rata-rata
request.

Alternatif: - **Fixed window:** sederhana, tetapi burst dapat terjadi di
batas antar-window. - **Sliding window:** lebih akurat, tetapi lebih
kompleks. - **Token bucket:** dipilih untuk burst terbatas dan kontrol
rata-rata request.

Login abuse juga mempertimbangkan kegagalan autentikasi per account.

### Counter storage v1

Gunakan **in-memory store**.

Konsekuensi: - Counter hilang saat proses restart. - Counter tidak
dibagikan antar-instance. - Setiap instance memiliki counter sendiri. -
Tidak cocok untuk horizontal scaling. - Counter harus memiliki expiry
dan cleanup agar memori tidak tumbuh tanpa batas.

**Batasan v1: satu instance API.** Jika berkembang menjadi
multi-instance, evaluasi shared store seperti Redis atau solusi
distributed rate limiting lain. Redis tidak digunakan untuk counter rate
limiting v1.

### Reverse proxy

Reverse proxy di luar scope v1. Rate limiter menggunakan alamat IP yang
langsung terlihat Node.js. Jangan mempercayai `X-Forwarded-For` secara
membabi buta.

Jika reverse proxy diperkenalkan: - Pelajari Express `trust proxy`. -
Tetapkan proxy yang dipercaya. - Pastikan forwarded header berasal dari
proxy tepercaya. - Jangan menerima IP dari header yang dapat dipalsukan
client.

### Response dan threshold

Limit terlampaui menghasilkan `429 Too Many Requests`, dengan
`Retry-After` jika relevan:

``` http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
```

``` json
{
  "error": {
    "code": "RATE_LIMIT_EXCEEDED",
    "message": "Too many requests. Please try again later."
  }
}
```

Exact threshold belum diputuskan. Konfigurasikan dan tuning berdasarkan
kapasitas server serta pola penggunaan, bukan hardcode tersebar.

### Trade-off

In-memory sederhana dan tanpa dependency tambahan, tetapi tidak
konsisten untuk multi-instance dan bukan perlindungan kuat terhadap
serangan terdistribusi. Ini batasan yang diterima untuk v1.

## 6. SEC-04 --- Input & Resource Limits

**Status: DECIDED**

### Request body

JSON request body maksimum **1 MB**. Body terlalu besar menghasilkan
`413 Content Too Large`. Tidak ada kebutuhan upload file pada scope v1.

Pembatasan dilakukan pada HTTP parser sebelum pemrosesan lebih lanjut.
Zod saja tidak cukup untuk melindungi server dari body sangat besar
karena body sudah perlu dibaca/diparsing.

### Field length limits

  Field                 Minimum           Maximum
  ------------------- --------- -----------------
  Organization name           1      100 karakter
  Project name                1      100 karakter
  Issue title                 1      200 karakter
  Issue description           0   10.000 karakter
  Comment body                1    5.000 karakter
  Email                       1      254 karakter

Batas Zod dan database harus konsisten.

### Validation

-   Zod memvalidasi struktur, tipe, dan aturan field.
-   HTTP parser membatasi body sebelum validasi schema.
-   Body terlalu besar: `413`.
-   Syntax/query tidak valid: `400`.
-   Request dapat dipahami tetapi melanggar validation/domain rule:
    `422` sesuai kontrak API.

### Query, pagination, dan sorting

Mengikuti API-04: - Default limit 20, maximum 100. - Limit di luar
rentang ditolak dengan `400`. - Cursor opaque dan divalidasi. -
`totalCount` mengikuti filter dan tenant authorization scope.

Batasi panjang search query, jumlah filter, nilai dalam filter array,
panjang/format cursor, dan field sorting yang diperbolehkan. Jangan
menerima nama kolom database secara bebas sebagai sorting parameter;
gunakan allowlist dan mapping server-side.

Search Issue v1 dibatasi per Project: - Title/description:
case-insensitive substring. - Issue number: exact numeric match. - Tidak
ada fuzzy, semantic, atau global search v1.

### Nested request

Hindari nested request yang tidak diperlukan. Gunakan request DTO
eksplisit dan relatif datar. Jika nested input dibutuhkan, batasi
kedalaman dan kompleksitas.

### Alternatif dan trade-off

Hanya Zod lebih sederhana, tetapi tidak cukup membatasi payload sangat
besar sebelum parsing. HTTP parser limit + Zod dipilih karena
masing-masing memiliki tanggung jawab jelas.

Batas ketat dapat membatasi kebutuhan pengguna; batas longgar
meningkatkan risiko resource exhaustion. Nilai dapat ditinjau ulang
berdasarkan kebutuhan domain dan evidence.

## 7. SEC-05 --- CORS & Security Headers

**Status: DECIDED**

### CORS

Gunakan **explicit origin allowlist**: - Origin frontend dikonfigurasi
melalui environment variable. - Tidak menggunakan wildcard origin. -
Hanya method HTTP yang diperlukan yang diizinkan. - Izinkan header yang
diperlukan, termasuk `Authorization`, `Content-Type`, dan
`Idempotency-Key`. - Credentialed CORS tidak diaktifkan karena
autentikasi menggunakan Bearer token, bukan cookie.

CORS mengatur akses lintas-origin oleh browser. CORS bukan
authentication atau authorization. `curl`, backend service, dan script
non-browser tidak dibatasi oleh CORS browser.

### Security headers

Gunakan Helmet sebagai baseline dan tinjau header sesuai fungsi API.

  -----------------------------------------------------------------------
  Header                              Tujuan
  ----------------------------------- -----------------------------------
  `X-Content-Type-Options: nosniff`   Mencegah MIME sniffing

  `X-Frame-Options: DENY`             Mencegah halaman ditampilkan dalam
                                      frame

  `Referrer-Policy`                   Mengontrol informasi referrer

  `Strict-Transport-Security`         Menginstruksikan browser
                                      menggunakan HTTPS setelah menerima
                                      kebijakan

  Content Security Policy             Mengontrol sumber resource browser
  -----------------------------------------------------------------------

HSTS hanya aktif pada deployment HTTPS. CSP tidak diwajibkan untuk API
JSON murni.

### Alternatif dan trade-off

Wildcard mudah tetapi terlalu terbuka. Dynamic origin reflection
berbahaya jika tidak divalidasi. Allowlist dipilih karena terkontrol,
dengan biaya konfigurasi origin per environment.

## 8. SEC-06 --- Session Security

**Status: DECIDED pada kebijakan server-side**

### Strategi autentikasi

-   Opaque random token sepanjang 32 byte.
-   Client mengirim melalui `Authorization: Bearer`.
-   Server menyimpan SHA-256 hash token di database, bukan token mentah.
-   Fixed expiration 7 hari.
-   Refresh melakukan token rotation.
-   Logout mencabut session saat ini.
-   JWT tidak digunakan untuk v1.
-   Cookie-based authentication tidak digunakan untuk v1.

### Mengapa SHA-256?

Password biasanya memiliki entropy rendah dan dapat ditebak, sehingga
membutuhkan password hashing mahal seperti Argon2id. Token random 32
byte memiliki entropy 256-bit; cryptographic hash cepat seperti SHA-256
sesuai untuk menyimpan verifier token dan lookup.

### Fixed expiration

Session berlaku 7 hari sejak dibuat. Aktivitas tidak otomatis
memperpanjang masa berlaku. Refresh secara eksplisit menerbitkan session
baru dengan masa berlaku baru.

Sliding expiration tidak dipilih untuk v1 karena fixed expiration lebih
mudah diprediksi dan dikelola.

### Refresh rotation

-   Token lama dicabut.
-   Token baru diterbitkan.
-   Pencabutan dan pembuatan session baru dilakukan atomik.
-   Dua refresh request bersamaan dengan token sama tidak boleh
    menghasilkan dua session baru.

### Refresh token reuse

-   Token lama yang sudah dirotasi selalu ditolak.
-   Reuse dicatat sebagai security event.
-   Reuse token lama tidak otomatis mencabut session baru.
-   Jika client kehilangan response yang berisi token baru, pengguna
    mungkin perlu login kembali.
-   Tidak ada replay-safe recovery mechanism dalam kebijakan v1 saat
    ini.

Trade-off: keamanan dan kesederhanaan diprioritaskan daripada pemulihan
otomatis yang lebih kompleks.

### Logout

Logout mencabut session saat ini. Tidak otomatis mencabut seluruh
session pengguna. Logout all sessions belum menjadi kebutuhan v1.

### Alternatif JWT

JWT membawa claims bertanda tangan dan dapat diverifikasi tanpa database
lookup untuk setiap access token.

Kelebihan: verifikasi lokal lintas-service dan cocok untuk distributed
architecture/interoperabilitas identity provider.

Kekurangan: revocation lebih rumit jika stateless, serta perlu
pengelolaan signing key, claims, expiry, refresh, dan validation.

JWT tidak ditolak permanen. Evaluasi kembali jika kebutuhan distributed
services, OAuth/OIDC, atau interoperability berubah.

### Alternatif cookie-based authentication

Cookie dapat membawa opaque token yang sama, tetapi browser mengirim
cookie otomatis sesuai aturan domain/path/SameSite.

Bearer dipilih karena client mengirim credential secara eksplisit dan
proyek berorientasi API untuk berbagai jenis client.

Trade-off: - Bearer token yang dapat dibaca JavaScript berisiko dicuri
melalui XSS. - HttpOnly cookie mengurangi akses JavaScript ke token,
tetapi cookie authentication harus mempertimbangkan CSRF.

Tidak ada klaim bahwa Bearer atau cookie selalu lebih aman. Threat model
dan jenis client menentukan pilihan.

### Browser token storage masih terbuka

Strategi penyimpanan token pada browser client belum diputuskan. Ini
harus diselesaikan sebelum browser authentication dirilis. Keputusan
Bearer authentication tidak otomatis menyelesaikan keamanan penyimpanan
token.

## 9. SEC-07 --- Data & Tenant Protection

**Status: DECIDED**

### Tenant isolation

Semua akses resource tenant harus dibatasi berdasarkan tenant scope.

Alur: 1. Authenticate user. 2. Resolve active membership. 3. Resolve
resource dalam tenant scope. 4. Check permission. 5. Execute operation.

Aturan: - Active membership wajib diverifikasi. - Authorization
dilakukan server-side. - Deny by default. - `organizationId` dari client
bukan bukti hak akses. - ID resource yang sulit ditebak bukan kontrol
authorization. - Object-level authorization wajib pada setiap endpoint.

### Tenant-scoped query

Hindari query yang hanya mencari resource berdasarkan ID:

``` ts
const issue = await prisma.issue.findUnique({
  where: { id: issueId },
});
```

Gunakan tenant scope:

``` ts
const issue = await prisma.issue.findFirst({
  where: {
    id: issueId,
    organizationId: activeOrganizationId,
  },
});
```

Pemeriksaan permission tetap diperlukan setelah resource ditemukan.

### Error visibility

  Kondisi                                          Response
  ------------------------------------------------ ----------
  Resource berada di tenant lain                   `404`
  User tidak memiliki active membership            `404`
  Membership aktif tetapi tidak punya permission   `403`
  Resource tidak ditemukan                         `404`

Berlaku konsisten pada GET, update, archive/restore, search, filtering,
pagination, `totalCount`, nested resource, dan relationship resolution.

### Database integrity

Database constraints menjadi lapisan integritas tambahan: - Composite
foreign key memastikan Issue dan Project berada dalam Organization yang
sama. - Assignee mengacu pada Membership dalam Organization terkait. -
Unique constraints menjaga business uniqueness. - Partial unique index
menjaga Invitation aktif.

Authorization menentukan siapa yang boleh melakukan operasi. Database
constraints memastikan data tidak melanggar aturan integritas, termasuk
ketika ada bug atau request bersamaan.

### Sensitive data exposure

-   Gunakan explicit DTO.
-   Jangan mengirim password hash atau session token hash.
-   Jangan mengekspos metadata internal yang tidak diperlukan.
-   Activity metadata tidak boleh memuat Comment body atau secret.
-   Error response tidak membocorkan detail internal.

### PostgreSQL Row-Level Security

RLS tidak digunakan pada v1.

Kelebihan RLS: defense in depth dan database dapat menegakkan row-level
policy jika aplikasi lupa tenant filter.

Kekurangan: perlu tenant context per transaksi/connection, perhatian
pada connection pooling, serta integrasi ORM dan debugging lebih
kompleks.

Trade-off: tanpa RLS, aplikasi memikul tanggung jawab lebih besar untuk
tenant scoping. Automated tenant isolation tests wajib.

## 10. SEC-08 --- Secrets & Dependencies

**Status: DECIDED**

### Secret management

Contoh secret: `DATABASE_URL`, `POSTGRES_PASSWORD`, email provider API
key, dan external service credentials.

Aturan: - Secret tidak boleh masuk Git. - Jangan hardcode secret di
source code atau Docker image. - `.env` harus di-ignore. -
`.env.example` hanya berisi placeholder. - Production secret disediakan
melalui environment/deployment platform. - Secret manager khusus belum
diperlukan untuk v1. - Environment variable bukan sistem secret
management otomatis aman; akses process, debugging, crash dump, dan
konfigurasi deployment tetap perlu dikendalikan.

### Log redaction

Pino redaction wajib untuk: - Password. - Authorization header. - Bearer
token. - Session token. - `DATABASE_URL`. - API keys. - Sensitive
request body fields.

Jangan mencatat seluruh request body secara otomatis. Redaction
dikonfigurasi terpusat; jangan bergantung pada ingatan setiap developer.

### Dependency security

-   Gunakan dependency yang masih dipelihara.
-   Periksa vulnerability advisories.
-   Lockfile wajib masuk Git.
-   CI menggunakan frozen lockfile.
-   Dependency baru harus direview.
-   Update dependency secara teratur.
-   Jangan mengabaikan vulnerability hanya karena aplikasi berjalan
    normal.

Tool yang dapat digunakan: - `pnpm audit`. - GitHub Dependabot. - GitHub
dependency review. - GitHub Actions security checks.

### Supply-chain security

`pnpm-lock.yaml` meningkatkan reproducibility, tetapi tidak menjamin
dependency bebas malicious code.

Aturan: - Lockfile masuk Git. - CI menggunakan frozen lockfile. -
Perubahan dependency direview melalui pull request. - Hindari dependency
yang tidak diperlukan. - Batasi lifecycle scripts yang tidak dibutuhkan.

### Secret rotation

Untuk v1, prosedur manual secret rotation harus tersedia dan
terdokumentasi, misalnya mengganti database password, mengganti email
API key, dan mencabut credential terkompromi. Automated secret rotation
di luar scope v1.

## 12. Security testing requirements

Kebijakan harus dibuktikan melalui pengujian.

### Password dan authentication

-   Password tidak pernah disimpan plaintext.
-   Hash menggunakan Argon2id.
-   Login untuk email tidak ditemukan dan password salah memberi respons
    generik.
-   Dummy verification berjalan untuk email tidak ditemukan.
-   Progressive throttling bekerja sesuai konfigurasi.
-   Security event tidak memuat credential mentah.

### Rate limiting

-   Request di atas limit menghasilkan `429`.
-   `Retry-After` dikirim jika relevan.
-   Counter memiliki expiry dan cleanup.
-   Perilaku restart sesuai batasan in-memory v1.
-   Per-IP dan per-account limiter diuji.

### Input limits

-   Body di atas 1 MB ditolak.
-   Field di atas batas ditolak.
-   Invalid cursor dan sorting ditolak.
-   Pagination maksimum 100 ditegakkan.
-   Query/filter limits diterapkan.

### CORS dan headers

-   Origin allowlist diterima.
-   Origin tidak diizinkan tidak mendapat CORS permission.
-   Wildcard tidak digunakan.
-   Security headers yang dipilih hadir.
-   HSTS hanya aktif pada HTTPS deployment.

### Session security

-   Token mentah tidak disimpan di database.
-   Expired/revoked token ditolak.
-   Refresh rotation atomik.
-   Concurrent refresh tidak menghasilkan dua session baru.
-   Reuse token lama ditolak dan dicatat.
-   Logout mencabut session yang digunakan.

### Tenant isolation

-   Tenant A tidak dapat membaca resource tenant B.
-   Tenant A tidak dapat mengubah atau mengarsipkan resource tenant B.
-   Search dan pagination tidak membocorkan data tenant lain.
-   `totalCount` mengikuti tenant scope.
-   Membership dan permission menghasilkan perilaku sesuai kontrak.

### Secrets dan dependencies

-   Secret tidak muncul di Git.
-   Pino redaction menutupi credential.
-   CI menggunakan frozen lockfile.
-   Dependency changes direview.
-   Vulnerability checks dijalankan sesuai kebijakan CI.

## 14. Change management

Setiap perubahan terhadap Security Baseline harus: 1. Mengidentifikasi
keputusan yang berubah. 2. Menjelaskan alasan dan evidence. 3. Menilai
dampak keamanan dan operasional. 4. Membandingkan alternatif relevan. 5.
Menilai apakah perubahan memperlemah atau memperkuat kontrol. 6.
Memperbarui dokumentasi dan automated tests. 7. Mencatat keputusan dan
tanggal revisi.

Perubahan scope seperti multi-instance, browser client, reverse proxy,
atau identity provider harus memicu evaluasi ulang terhadap keputusan
terkait.

**Prinsip akhir:** Security Baseline bukan janji bahwa sistem bebas
vulnerability. Ia adalah seperangkat kontrol yang disengaja, memiliki
alasan, memiliki batasan yang diketahui, dan dapat diuji.
