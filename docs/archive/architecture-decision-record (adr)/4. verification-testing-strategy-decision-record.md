## 3. VT-01 — Testing Pyramid

**Decision:** Use three testing layers: Unit, Integration, and E2E.

### Unit Testing
Tests isolated units of business logic without requiring PostgreSQL or an HTTP server.

### Integration Testing
Tests interactions between application components and real dependencies, particularly PostgreSQL.

### End-to-End Testing
Tests complete business workflows through the HTTP API.

### Rules

1. Unit and Integration tests form the majority of the test suite.
2. E2E tests focus on critical business workflows.
3. Testing distribution follows project risks and architecture.
4. Code coverage alone is not a sufficient measure of test quality.
5. Tests must verify behavior and invariants, not merely execute code without errors.
6. Use real dependencies when their actual behavior is the subject of testing.

No universal test ratio is mandated.

---

## 4. VT-02 — Unit Testing

**Decision:** Prioritize isolated domain logic and business rules.

### Test coverage areas

| Component | Example |
|---|---|
| Domain rules | Valid and invalid Issue transitions |
| Authorization policy | Role permission checks |
| Validation | Input structure and field rules |
| Normalization | Consistent email normalization |
| Utility | Expiration and pagination calculations |
| Error mapping | Domain errors mapped to HTTP errors |

### Rules

1. Unit tests do not require PostgreSQL or an HTTP server.
2. Use mocks and stubs selectively to isolate dependencies.
3. Mock clocks when testing time-dependent logic.
4. Avoid testing irrelevant internal implementation details.
5. Important business rules must cover valid, invalid, and boundary cases.
6. Do not treat 100% code coverage as the primary objective.

---

## 5. VT-03 — Integration Testing

**Decision:** Use real PostgreSQL for database integration testing.

### Test coverage areas

- Prisma query behavior.
- Foreign key and unique constraints.
- Database transactions.
- Transaction rollback.
- Repository tenant scoping.
- Session persistence and lookup.
- Migration execution.

### Rules

1. Use a dedicated PostgreSQL test database.
2. Run database migrations before the test suite.
3. Each test must have isolated data.
4. Verify database state after successful and failed operations.
5. Do not mock Prisma when testing actual database behavior.
6. Do not automatically rely on one outer transaction rolled back after every test.

### Example: Transaction Rollback

If Activity creation fails during Issue creation:

- Issue must not persist.
- Issue counter must not increment.
- Activity must not persist.

The test must verify the resulting database state, not merely assert that an exception was thrown.

## 6. VT-04 — API / E2E Testing

**Decision:** Use Supertest to test HTTP endpoints through the Express application.

### Rules

1. Tests must exercise the HTTP request and response path.
2. Middleware, routing, validation, authentication, authorization, and database interactions must be included according to test scope.
3. E2E tests prioritize critical business workflows.
4. Verify HTTP status, response envelope, important headers, and database state.
5. Include failure scenarios such as invalid input, unauthenticated access, forbidden access, missing resources, conflicts, and domain rule violations.
6. Keep Express `app` separate from `server`, allowing tests to run without opening a network port.
7. Use controlled test tokens and fixtures.

### Priority E2E workflows

**Workflow A: Account and Organization**
- Register
- Login
- Create Organization

**Workflow B: Invitation**
- Create Invitation
- Accept Invitation
- Verify active Membership

**Workflow C: Project and Issue**
- Create Project
- Create Issue
- Assign Issue

**Workflow D: Membership Revocation**
- Revoke Membership
- Verify assigned Issues become unassigned

API integration tests and E2E tests may use the same library. Their distinction is test scope and purpose.

## 7. VT-05 — Authorization & Tenant Isolation

**Decision:** Authorization matrix and tenant isolation are mandatory test suites.

### Authorization testing

Test permissions across:

- OWNER
- ADMIN
- MEMBER

Verify both allowed and forbidden operations.

Include special domain rules:

- Last Owner protection.
- Owner management restrictions.
- Admin self-promotion restrictions.
- Comment ownership.
- Membership revocation.
- Invitation permissions.

### Tenant isolation testing

Use at least two independent Organizations with separate users and resources.

Test:

1. Direct resource access through IDs.
2. Nested resource access.
3. Search results.
4. Pagination.
5. Count queries.
6. Relationship resolution.
7. Inactive or missing Membership.
8. Manipulated request IDs, body fields, and query parameters.

### Expected HTTP behavior

| Scenario | Expected status |
|---|---|
| Missing resource | 404 |
| Cross-tenant resource access | 404 |
| No active Membership | 404 |
| Active Membership without permission | 403 |

### Additional requirement

Verify that rejected operations do not cause unauthorized database mutations.

Testing only successful Owner operations is insufficient. Forbidden operations must be explicitly tested.

## 8. VT-06 — Concurrency & Failure Testing

**Decision:** Maintain dedicated tests for critical concurrency and failure invariants.

### Concurrency scenarios

| Scenario | Expected behavior |
|---|---|
| Concurrent Issue creation | No duplicate Issue numbers |
| Concurrent Invitation acceptance | Only one succeeds |
| Membership revoke vs Issue update | Result follows lock acquisition order |
| Membership revoke vs re-invite | No inconsistent Membership state |
| Concurrent updates with same version | Only one succeeds |
| Duplicate Idempotency-Key | Business operation is not executed twice |

### Failure scenarios

| Scenario | Expected behavior |
|---|---|
| Activity creation fails | Business mutation rolls back |
| Issue creation fails | Counter increment rolls back |
| Required Notification creation fails | Associated business operation rolls back |
| Email provider fails | Invitation remains persisted |
| Outbox worker fails | Event remains available for retry |
| Database connection fails | No false success response |

### Rules

1. Use real PostgreSQL and real transactions.
2. Run competing operations concurrently.
3. Use explicit synchronization mechanisms to reproduce race conditions.
4. Verify database state after successful and failed operations.
5. Test Outbox retry and duplicate delivery behavior.
6. Critical concurrency tests must be repeatable.
7. Test deadlock or serialization failure handling where those mechanisms are used.

### Concurrency vs Load Testing

- Concurrency testing verifies correctness when operations compete.
- Load testing verifies performance under high workload.

Load and performance testing are handled separately during operational readiness.

## 9. VT-07 — Test Data & Environment

**Decision:** Use a dedicated, isolated, deterministic testing environment.

### Database environment

1. Dedicated PostgreSQL test database.
2. Separate from development and production.
3. Safety guard prevents tests from accessing development or production databases.
4. Run versioned migrations before the test suite.
5. Concurrency tests use independent connections and transactions.

### Test Fixtures and Factories

**Fixture:** predefined data for a specific scenario.

**Factory:** dynamically creates valid test data.

Example factory functions:

```ts
createTestUser()
createTestOrganization()
createTestMembership()
createTestProject()
createTestIssue()
```

Factories reduce repetitive setup while respecting actual database relationships and constraints.

### Test isolation

1. Tests must not depend on previous test results.
2. Avoid shared mutable state.
3. Use appropriate cleanup or database isolation strategies.
4. Concurrency tests require genuinely independent transactions and connections.

### Deterministic testing

- Use fixed or fake clocks for expiration scenarios.
- Avoid unnecessary dependence on real-time clock behavior.
- Use explicit data for important scenarios.
- Never rely on database ordering without an explicit ordering clause.

### CI consistency

1. CI uses PostgreSQL with the same or compatible version as development.
2. Migrations run before tests.
3. Environment configuration is controlled.
4. Tests fail if the database is unavailable or incorrectly configured.
5. Failed tests must not be ignored merely to obtain a green pipeline.

## 10. Cross-Cutting Principles

The approved strategy establishes these principles:

1. Test business behavior, not just implementation details.
2. Use real PostgreSQL when database behavior is being verified.
3. Verify database state after important operations.
4. Treat tenant isolation and authorization as critical security properties.
5. Explicitly test failure paths and concurrent operations.
6. Keep tests isolated and deterministic.
7. Use E2E testing selectively for critical business workflows.
8. Do not use code coverage as the sole measure of test quality.

---

## 11. Implementation Verification Requirements

During implementation, verify:

- All permitted and forbidden role operations.
- Cross-tenant access through every relevant query path.
- Transaction rollback for critical business operations.
- Unique constraints under concurrent requests.
- Invitation expiry and concurrent acceptance.
- Membership revocation and Issue unassignment.
- OCC stale-version conflicts.
- Idempotency behavior under duplicate requests.
- Outbox retry and duplicate delivery.
- Migration reproducibility from a clean database.
- CI and local test environment consistency.

These are requirements for future implementation and verification, not claims of completed test coverage.
