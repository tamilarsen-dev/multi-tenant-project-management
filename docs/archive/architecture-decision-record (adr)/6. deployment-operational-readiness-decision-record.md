# Deployment & Operational Readiness Decision Record

**Project:** Multi-Tenant Project Management API  
**Scope:** Version 1 (V1)  
**Status:** Decisions Approved

## 1. Purpose

Dokumen ini mencatat keputusan operasional yang harus menjadi dasar deployment dan pengoperasian V1. Tujuannya memastikan aplikasi bukan hanya dapat berjalan, tetapi juga dapat dipantau, dipulihkan, diamankan, dan dipelihara.

## 2. OR-01: Hosting & Infrastructure

**Keputusan:**
- V1 menggunakan satu VPS.
- API dan PostgreSQL berjalan dalam container Docker Compose terpisah.
- PostgreSQL hanya dapat diakses melalui internal Docker network.
- PostgreSQL menggunakan persistent volume.
- Backup disimpan di luar VPS.
- Kubernetes, autoscaling, dan multi-instance tidak digunakan pada V1.
- Single point of failure diterima sebagai keterbatasan V1.
- Managed database dapat dievaluasi kembali jika kebutuhan meningkat.

**Trade-off:** Infrastruktur sederhana dan biaya awal rendah, tetapi satu VPS menjadi titik kegagalan utama.

## 3. OR-02: Environment Configuration

**Keputusan:**
- Lingkungan dipisahkan menjadi Development, Staging, dan Production.
- Validasi konfigurasi menggunakan Zod saat startup.
- Konfigurasi wajib yang tidak valid atau hilang menyebabkan startup gagal.
- Production secrets diinjeksi melalui deployment environment.
- Secrets tidak boleh masuk Git, Docker image, atau build artifact.
- `.env` hanya untuk penggunaan lokal.
- `.env.example` hanya berisi placeholder.
- Akses secrets dibatasi.
- Prosedur rotasi secrets dilakukan secara manual untuk V1.
- Dedicated secret manager ditunda.

## 4. OR-03: Health Checks

**Keputusan:**

Dua jenis health check digunakan:

- **Liveness:** memeriksa apakah proses aplikasi masih hidup; tidak bergantung pada database.
- **Readiness:** memeriksa apakah aplikasi dan dependency wajib, terutama PostgreSQL, siap menerima trafik.

Ketentuan:
- Endpoint health check dapat diakses tanpa autentikasi.
- Pemeriksaan database harus ringan dan memiliki timeout.
- Response tidak boleh mengungkap informasi sensitif.
- Readiness failure tidak otomatis me-restart aplikasi.
- Deployment dianggap berhasil setelah readiness check dan smoke test berhasil.
- Endpoint `/healthz` yang sudah ada dapat disesuaikan atau dipisah menjadi endpoint liveness dan readiness.

## 5. OR-04: Observability

**Keputusan:**

Logging:
- Menggunakan Pino structured logging.
- Request ID digunakan untuk korelasi log.
- Secrets dan informasi sensitif harus di-redact.
- Full request body tidak boleh dicatat secara default.

Metrics:
- Request rate.
- Error rate.
- Latency.
- CPU dan memory.
- Database connection usage.
- Database query duration.

Latency dipantau menggunakan p50, p95, dan p99.

Monitoring dan alerting diperlukan untuk mendeteksi kondisi operasional yang bermasalah.

Distributed tracing dan OpenTelemetry ditunda untuk V1. Alert thresholds dan log retention ditentukan setelah tersedia workload baseline.

## 6. OR-05: Backup & Recovery

**Keputusan:**
- PostgreSQL menggunakan logical backup melalui `pg_dump`.
- Backup dijalankan otomatis setiap hari.
- Retention:
  - 7 backup harian.
  - 4 backup mingguan.
- Backup disimpan di luar VPS.
- Backup dienkripsi saat transit dan saat disimpan.
- Target awal RPO adalah 24 jam.
- Target awal RTO adalah 4 jam.
- Restore diuji secara berkala ke database terpisah.
- Prosedur backup dan recovery harus didokumentasikan.
- WAL archiving dan Point-in-Time Recovery (PITR) ditunda untuk V1.

**Catatan:** Jadwal backup harian saja tidak menjamin RPO 24 jam. Keberhasilan backup, jadwal aktual, dan kemampuan restore harus dipantau.

## 7. OR-06: Incident Response

**Keputusan:**

Incident adalah gangguan yang memengaruhi availability, security, integrity, atau performance sistem.

Severity classification:

| Severity | Kriteria |
|---|---|
| SEV-1 | Gangguan kritis dan luas, misalnya API dan database tidak tersedia |
| SEV-2 | Fungsi utama gagal secara luas, misalnya login atau Create Issue |
| SEV-3 | Gangguan terbatas pada fitur atau endpoint tertentu |
| SEV-4 | Dampak rendah, seperti bug minor atau masalah kosmetik |

Incident lifecycle:

**Detect → Triage → Mitigate → Resolve → Verify → Review**

Prioritas utama adalah membatasi dampak dan memulihkan layanan sebelum melakukan investigasi akar masalah secara mendalam.

Dokumentasi insiden mencakup:
- Waktu mulai dan selesai.
- Severity.
- Dampak terhadap pengguna.
- Sistem yang terdampak.
- Dugaan penyebab dan root cause setelah diketahui.
- Mitigasi dan pemulihan.
- Tindakan pencegahan.

Insiden besar mendapatkan postmortem yang berfokus pada sistem dan proses, bukan menyalahkan individu.

Runbook V1 mencakup API, PostgreSQL, disk, backup, deployment, dan credential.

Tidak diperlukan dedicated incident management platform untuk V1.

## 8. OR-07: Performance & Capacity

**Keputusan:**
- Pendekatan measurement-first: ukur sebelum melakukan optimasi.
- Monitor throughput, latency, error rate, CPU, memory, disk, database query duration, dan connection usage.
- Gunakan p50, p95, dan p99 untuk latency.
- Target kapasitas numerik tidak ditentukan sebelum tersedia workload baseline.
- Load testing digunakan untuk mengukur kapasitas awal.
- Profiling dilakukan sebelum optimasi.
- Vertical scaling menjadi strategi awal.
- Horizontal scaling ditunda sampai terdapat kebutuhan nyata dan arsitektur mendukungnya.
- Query optimization, indexing, caching, dan pemisahan database dievaluasi berdasarkan bukti bottleneck.

**Trade-off:** Vertical scaling lebih sederhana untuk V1, tetapi memiliki batas kapasitas dan tidak menghilangkan single point of failure.

## 9. OR-08: Operational Security

**Keputusan:**

Server access:
- SSH menggunakan key-based authentication.
- Password authentication untuk SSH dinonaktifkan.
- Direct root login dinonaktifkan.
- Deployment menggunakan akun non-root dengan privilege minimum.
- Akses SSH dibatasi melalui firewall jika memungkinkan.

Network:
- Firewall hanya membuka port yang diperlukan.
- PostgreSQL tidak diekspos ke internet.
- HTTPS wajib sebelum API digunakan secara publik.

Docker dan OS:
- Container menggunakan least privilege.
- Docker socket tidak di-mount ke container API.
- Docker image menggunakan versi spesifik, bukan tag `latest`.
- OS dan security patches diperbarui secara berkala.

Credential:
- Akses production secrets dibatasi.
- Credential Development, Staging, dan Production dipisahkan.
- Credential yang bocor harus di-revoke atau di-rotate dan diinvestigasi.
- Secrets tidak boleh masuk log, image, atau repository.

Security maintenance:
- Dependency vulnerabilities diperiksa secara berkala.
- Aktivitas SSH dan server yang mencurigakan dipantau.
- Kapasitas disk dipantau.
- Prosedur patching dan credential rotation didokumentasikan.

## 10. Deferred Decisions

Hal-hal berikut sengaja belum ditentukan secara numerik atau teknis karena membutuhkan bukti dari sistem berjalan:

- Alert thresholds dan log retention.
- Target throughput dan latency.
- Kapasitas maksimum VPS.
- Threshold untuk vertical scaling.
- Kebutuhan horizontal scaling.
- Kebutuhan managed database.
- Penggunaan distributed tracing.
- Penggunaan PITR dan WAL archiving.
- Pemilihan hosting provider.
- Kebutuhan dedicated secret manager dan incident management platform.

Penundaan ini bukan berarti aspek tersebut diabaikan. Keputusan akan dibuat ketika data operasional tersedia atau sebelum sistem memasuki production jika menjadi persyaratan wajib.

## 11. Operational Readiness Principles

Prinsip yang harus dipertahankan:

1. Infrastruktur sederhana selama kebutuhan masih sederhana.
2. Production harus memiliki konfigurasi dan secrets terpisah.
3. Kesehatan aplikasi dan kesiapan dependency harus dapat diperiksa.
4. Log dan metrics harus membantu diagnosis, bukan membocorkan secrets.
5. Backup harus dapat dipulihkan, bukan sekadar berhasil dibuat.
6. Insiden harus memiliki prosedur respons yang jelas.
7. Optimasi harus didasarkan pada pengukuran.
8. Server dan deployment harus mengikuti prinsip least privilege.

## 12. Change Management

Keputusan dalam dokumen ini merupakan baseline V1.

Perubahan keputusan harus:
- Memiliki alasan teknis atau operasional.
- Mempertimbangkan dampak terhadap keamanan, biaya, kompleksitas, dan reliabilitas.
- Didokumentasikan.
- Memiliki strategi migrasi jika memengaruhi sistem yang sudah berjalan.
